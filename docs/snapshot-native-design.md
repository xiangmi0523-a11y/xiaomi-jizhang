# 方案 A 实施设计：原生持久化回执、原子提交、批次快照、仅本机恢复

> 状态：阶段 1（接口和状态机设计审查），实施前写定。分支 `feat/h3-frontend`。
> 结论：**原子性可以保证**（见第 4、9 节），因此继续实施。
> 唯一的残余窗口与 App 现在的保存方式相同：用户改动后约 250 毫秒的保存防抖内被杀，这次改动会丢。本方案没有扩大这个窗口。

## 1. 现有提交顺序（改动前，逐步核对过代码）

| 位置 | 做什么 | 持久化方式 |
|---|---|---|
| `App.load`（`core.js`） | 启动时读账本：优先读原生启动脚本注入的 `__NATIVE_B64__`（`Documents/xiaomi-data.json`）；没有或损坏，就读 localStorage `xiaomi_ledger_v1` | — |
| `App.flush`（`core.js`） | 整份账本写 localStorage（**吞错误**），再发原生 `save` | 原生 `saveData`：`try? write(.atomic)`，**不 fsync、吞错误、没有回执** |
| `App.flush` 的包装 | `bridge.js` 一层（小组件），`cloud.js` 一层（有改动 5 秒后同步）。本方案**不增加**包装 | — |
| `C.sync`（`cloud.js`） | `busy` 互斥 →（有恢复任务时）`R.step` → `checkEpoch` → `rebase` 或普通同步 → 结束时 `App.flush`（`quiet`，这次不触发同步） | 同 `App.flush` |
| `C.rebase`（2B-2，改动前） | ① `conflicts.snapshot`：localStorage `xm_snap_rebase` 必须写成功，另发原生 `snapshot`（没有回执）<br>② 全量拉取（`await`），再读 epoch<br>③ 同步代码块：`pendingChanges` → `protect`（把**覆盖前的账本 + 冲突箱**写进 localStorage，必须成功）→ **原地改** `App.S` → `epoch = target` → `prune`<br>④ `C.sync` 结束时 `flush` | ③ 之后、④ 之前被杀：存储里是「旧数据 + 冲突箱 + 旧 epoch」，重启后会重新对齐（幂等） |

**问题：**
- 快照和冲突箱都必须写进 localStorage，单个来源只有约 524 万字符（实测）；
- 原生写入没有回执，也不 fsync；
- 只有一份快照；
- 对齐是原地修改 `App.S`，只靠「先存冲突箱」来保证安全。

## 2. 新模块和加载顺序

```
core … cloud → durable（新）→ conflicts → safety（新）→ restore → auth …
```

- `www/js/durable.js`（`App.durable`）：
  - 原生回执通道（编号、等待表、超时、页面实例随机数）；
  - 纯 JS SHA-256，从 `restore.js` 移过来，`restore.js` 改为引用这里的；
  - 快照的读、写、列出、删除（原生，或 localStorage 降级）；
  - **账本原子提交** `commitLedger`。
- `www/js/safety.js`（`App.safety`）：
  - 在账本副本上计算（`onCopy`）；
  - 写对齐快照；
  - 批次记录（`S.safety`）；
  - 清理；
  - 「从快照恢复本机」的状态机和界面。
- `conflicts.js`：`protect` 改为**只改内存**（持久化交给原子提交），并增加跨批次去重。冲突处理逻辑不变。
- `cloud.js`：`C.rebase` 改为「在副本上算出覆盖后的账本 → 写快照拿回执 → 原子提交 → 切换内存」；`C.sync` 增加「本机恢复后暂停同步」的判断。
- 所有改动都是直接改函数本身，**不新增任何全局函数包装**。

## 3. 原生接口 v1

### 3.1 能力声明

原生启动脚本注入 `window.__NATIVE_CAPS__ = { durableWrite: 1 }`。

前端只在 `durableWrite === 1`，并且 `webkit.messageHandlers.native` 存在时才走原生路径。版本号不同、或者没有这个声明，就走 localStorage 降级路径。降级路径同样要求写入成功，否则安全停止，**绝不伪造成功**。

### 3.2 请求

网页通过 `postMessage` 发送：

```js
{ type: 'durable', v: 1, op, id, ...参数 }
```

| op | 参数 | 原生层做什么 |
|---|---|---|
| `snapshotWrite` | `dir, name, content, bytes, sha256, meta` | ① 先核对 `content` 的 UTF-8 字节数和 SHA-256 与请求一致（传输校验）<br>② 把内容持久写入 `Documents/安全快照/<dir>/<name>`<br>③ 读回校验<br>④ 把 `meta`（含 `bytes`、`sha256`）持久写入 `<name>.meta.json` |
| `ledgerStage` | `content, bytes, sha256` | 传输校验 → 持久写入 `Documents/.xiaomi-data.next.json` → 读回校验 |
| `ledgerCommit` | `bytes, sha256` | 读出暂存文件，核对 → 原子改名替换 `xiaomi-data.json` → 同步目录 → 读回正式文件校验 |
| `ledgerDiscard` | — | 删除暂存文件（不存在也算成功） |
| `snapshotList` | — | 列出 `安全快照` 下所有批次目录里的快照：每个文件**重新计算** SHA-256，与 meta 比对，给出 `verified` |
| `snapshotRead` | `dir, name` | 读出内容，返回内容、实际字节数、SHA-256 和 meta |
| `snapshotDelete` | `dirs` | 逐个删除指定的批次目录：名字必须符合格式；不存在算成功（`absent`）；每个目录单独回报结果 |

**持久写入流程：**

1. 在同一目录建临时文件 `.<name>.<uuid>.tmp`（`open(O_CREAT|O_TRUNC|O_CLOEXEC)`）；
2. 循环 `write`，处理 `EINTR` 和短写；
3. `fcntl(F_FULLFSYNC)`，失败就退回 `fsync`，两个都失败就报错；
4. `close`，检查返回值，文件描述符只关一次；
5. `rename` 成正式文件；
6. 打开目录做 `F_FULLFSYNC` / `fsync`；
7. 不走缓存地读回，计算 SHA-256 并比对。

任何一步失败：删除临时文件，返回失败。**不使用 `try?`。**

**名字规则：**
- `dir` 只能是 `[A-Za-z0-9_-]{1,120}`；
- `name` 不能含 `/`、不能以 `.` 开头、必须以 `.json` 结尾、长度 ≤ 150；
- 不符合就返回 `bad_request`。

### 3.3 回执

原生层调用：

```js
App.durable.done(id, base64(JSON))
```

JSON 内容：

```js
{ v: 1, id, op, ok, code, message, bytes, sha256, items?, content?, meta? }
```

**前端判定为成功的条件（全部满足）：**
- 编号在等待表里（每个页面实例的随机数 + 序号）；
- 没有超时，也没有被页面重载丢弃；
- `v === 1`、`op` 一致；
- `ok === true`；
- 写类操作：回执里的 `bytes` 和 `sha256`（原生层读回正式文件算出来的）都等于前端事先算好的值。

**以下一律判失败：** 失败回执、超时、摘要不一致、字节数不一致、编号不认识、迟到的回执、重载前发出的请求的回执。迟到的回执直接丢弃，不会执行任何回调。

### 3.4 错误码和超时

| 错误码 | 含义 |
|---|---|
| `ENOSPC` | 空间不足（`EDQUOT` 也归这类） |
| `EACCES` / `EROFS` | 没有权限 / 只读 |
| `ENOENT` | 文件或目录不存在 |
| `EIO` | 其他读写错误 |
| `mismatch` | 读回的内容与请求不一致 |
| `transport` | 收到的内容与请求里声明的字节数或 SHA-256 不一致 |
| `stage_missing` / `stage_mismatch` | 提交时找不到暂存文件 / 暂存内容不对 |
| `bad_request` | 参数或名字不合法 |
| `unsupported_version` | 协议版本不支持 |

前端额外的错误码：
- `timeout`：超时；
- `no_native`：没有原生能力；
- `quota`：localStorage 配额不足。

| 超时 | 时长 |
|---|---|
| 写快照、暂存账本 | 20 秒 + 每 MB 4 秒 |
| 提交 | 15 秒 |
| 列出 | 20 秒 |
| 读取 | 30 秒 |
| 删除 | 15 秒 |

### 3.5 顺序

原生层所有持久化操作，包括原有的 `save`，都放在**同一个串行 IO 队列**里，执行顺序就是网页发送的顺序。所以：
- 先发的普通保存，会被后发的提交覆盖；
- 提交之后发出的普通保存，会写在提交之后。

### 3.6 版本兼容

- 请求带 `v`。原生层只接受 `v === 1`，其他版本回执 `unsupported_version`。
- 以后升级协议时：能力声明里写支持的最高版本，前端按两边都支持的版本发请求。
- 网页文件打包在 IPA 里，原生 App 里不会出现新旧版本混用。

### 3.7 启动时的恢复（原生 `bootstrapScript` 读正式文件之前，在 IO 队列里执行）

1. 删除 `Documents` 根目录和各个快照目录里残留的 `.*.tmp`。只删这一类，正式文件不碰。
2. 如果暂存文件 `.xiaomi-data.next.json` 还在，说明上次提交没完成：
   - 把它移到 `Library/Application Support/xm-diag/uncommitted-<时间>.json`（不在「文件」App 里显示，最多留 3 份）；
   - 注入 `window.__NATIVE_RECOVERY__`，网页记一条诊断日志。
3. 然后照常读取 `xiaomi-data.json`。

## 4. 账本原子提交 `App.durable.commitLedger(after, same, apply)`

- `after`：覆盖后完整账本的 JSON；
- `same()`：确认 `App.S` 和计算 `after` 时一样；
- `apply()`：把内存切换为新账本，同步执行。

### 原生路径

```
ledgerStage(after) ──回执成功──▶ same()? ──否──▶ ledgerDiscard，抛「需要重试」
                                 │是
                                 ▼
                       ledgerCommit ──回执成功──▶ same()? ──是──▶ apply()（同步）
                                                    │否
                                                    ▼
                         App.flush()（把当前内存重新写回正式文件），抛「需要重试」
```

### 降级路径（网页、PWA、没有能力声明）

```
same()? ──是──▶ localStorage.setItem(账本键, after)（必须成功）──▶ apply()（同步，没有 await）
```

### 各个时刻被杀之后的状态

正式文件只会经过一次原子改名，所以重启后读到的一定是一个完整的账本。

| 被杀的时刻 | 重启后读到 | 怎么继续 |
|---|---|---|
| 暂存前或暂存中 | 旧账本 | 旧账本的 epoch 也是旧的 → 下次同步重新对齐（冲突项编号相同，幂等） |
| 暂存后、提交前 | 旧账本；暂存文件被启动流程移走 | 同上 |
| 提交改名之后、回执到达之前 | 新账本（完整，含冲突箱和新 epoch） | 正常使用，不再对齐 |
| 回执之后、内存切换之前（只有几毫秒） | 新账本 | 同上 |

**提交之前，内存里不会出现新账本。** 判断「提交完成」只看回执，`apply` 只在回执成功之后执行。

**用户在等待回执期间改了账本**（`same()` 为假）：放弃这次提交，内存保持「旧账本 + 这次改动」，并立刻写回正式文件，然后重新对齐，这次改动会作为未同步修改进入冲突箱。唯一的风险是「提交改名完成」到「写回」之间的几毫秒里被杀：这时重启读到新账本，这次改动丢失。这与 App 现在「改动后 250 毫秒防抖内被杀就丢」是同一级别的窗口，没有扩大。

## 5. 新的对齐流程 `C.rebase(stat, info)`

1. 全量拉取（`await`）→ 再读一次 epoch，变了就停（与现在相同）。
2. **同步代码块**：
   - `before = JSON.stringify(App.S)`；
   - `next = App.safety.onCopy(...)`：在 `before` 的深拷贝上，用**现有的同一套代码**执行 `pendingChanges` → `protect`（只改内存，带跨批次去重）→ 覆盖各表 → `stateIn` → 重建同步基线 → `epoch = target` → `prune` → 记录批次（`S.safety.batches`）→ 需要时清除本机恢复的暂停状态。
   - **`App.S` 本身不被改动。**
3. `await App.safety.snapshot(batch, before)`：拿不到严格回执就抛错，**不提交、不改 epoch**。
4. `await App.durable.commitLedger(JSON.stringify(next), () => JSON.stringify(App.S) === before, () => { App.S = next; })`。
5. 第 3、4 步遇到「需要重试」时，最多重算 3 次（从第 2 步开始，复用已拉取的数据）。还不行就报错，下次同步再试。
6. 提示（文案与现在相同，可以由 `info` 定制）。

提交的是一份完整账本，覆盖后的各表、冲突箱、同步基线、epoch、批次记录都在一次原子提交里，不会出现半新半旧的状态。

## 6. 冲突箱和批次记录

### 冲突项

- 编号仍然是 `批次|表|键`，同一批次里按编号合并、已处理的不改（与现在相同）。
- **跨批次去重：** 新批次里某一项，如果已有**其他批次**的待处理项「表、键、类型、本机内容」都相同，就不再新建。内容不同说明是另一次修改，保留。

### 批次记录 `S.safety`

```js
S.safety = { v: 1, batches: { [批次]: { dir, kind, at, items, doneAt } } }
```

- `kind`：
  - `align`：对齐；
  - `restore`：自己恢复备份后的对齐；
  - `resume`：本机恢复后恢复云同步；
  - `protect`：本机恢复前的保护点。
- `items`：这个批次进冲突箱的条数。
- `doneAt`：批次内所有冲突项都处理完（包括「与云端一致」自动关闭的）那一刻的时间。条数为 0 的批次，在提交时就记为完成。`protect` 批次在本机恢复结束（恢复云同步或撤销）时才记为完成。
- 处理冲突（`resolve`）时，如果这是批次里最后一个待处理项，就写入 `doneAt`。

`S.safety` 只属于这台手机：导出备份时去掉；恢复备份时忽略备份里的；退出登录时随账本一起清空，磁盘上的快照因为归属无法判断，按规则保留。

## 7. 快照的存储和清理

### 存储位置

| 环境 | 位置 |
|---|---|
| 原生 App | `Documents/安全快照/<dir>/<文件名>.json`，旁边是 `.meta.json` |
| 降级路径 | localStorage 键 `xm_snap:<dir>:<文件名>`，值为 `{meta, data}`，一次 `setItem` |

**目录名（`dir`）由批次决定，同一批次重试时写同一个文件（原子替换，天然去重），不同批次互不覆盖：**
- 对齐：`e<epoch>-<uid前8位>`；
- 恢复云同步：`r<时间>-<uid前8位>`；
- 保护点：`p<时间>-<uid前8位>`。

**meta 内容：** `{ v, kind, batch, uid, at, from, to, label, bytes, sha256, counts }`

### 清理 `App.safety.housekeep()`

每 24 小时最多一次，在同步成功后异步执行，失败不影响记账。

**同时满足以下全部条件才删除，否则一律保留：**
- meta 可以读、`verified === true`；
- `meta.uid` 等于当前账号；
- 批次在 `S.safety.batches` 里，`doneAt` 存在，并且距今超过 30 天；
- 冲突箱里这个批次没有待处理项；
- 没有被恢复任务引用（`restore.js` 已应用、但还没对齐完成的那个批次）；
- 没有被本机恢复的暂停状态引用（保护点、被恢复的那份快照）。

**注意：** 「冲突箱是空的」不等于可以删除，因为处理过的冲突项 30 天后会被冲突箱清掉。所以只看批次记录里的 `doneAt`。

**删除方式：**
- 原生 `snapshotDelete` 逐个目录执行，每个目录单独回报结果；
- 重复执行是幂等的；
- 失败写入诊断日志（`App.safety.log`，最多 50 条，同时输出到控制台）。

**旧格式：** localStorage 里的旧键 `xm_snap_rebase`（2B-2 开发期间用的）按「批次未知」处理，永不自动删除。

### 「文件」App 里的可见性

`Info.plist` 已有 `UIFileSharingEnabled` 和 `LSSupportsOpeningDocumentsInPlace`，`Documents` 目录本来就在「文件」App 里可见（主账本 `xiaomi-data.json` 和「自动备份」文件夹现在就能看到）。

本方案：
- **不改**文件共享配置；
- 只在已经公开的 `Documents` 下新增「安全快照」文件夹；
- 暂存文件和临时文件以 `.` 开头；
- 诊断文件放在 `Library` 下，不公开。

是否真的可见，需要真机验证（列入真机待测清单）。

## 8. 「从快照恢复本机」状态机

```
正常 ──恢复到本机（校验、二次确认、写保护点、原子提交）──▶ 暂停同步（sync.hold）
暂停同步 ──「恢复云同步」──▶ 强制对齐（快照和本机的差异进冲突箱）──▶ 正常
暂停同步 ──「撤销本机恢复」（仅限恢复后没改过数据）──▶ 原子提交保护点 ──▶ 正常
```

### 恢复到本机

**前置条件：**
- 不在暂停同步状态；
- 没有进行中的云端恢复任务；
- 同步不在进行中；
- 快照 `verified`；
- `meta.uid` 等于当前账号。

**步骤：**

1. 读取快照（原生层读回并返回 SHA-256，前端再算一遍），再做结构校验：必需模块存在，`normalize` 之后条数不变。
2. 在副本上构造新账本 `R`：

   | 内容 | 来自 |
   |---|---|
   | 账单、账户、分类、预算、周期记账、`game`（含金币、签到、盲盒进度、猫咪）、智能预算、存钱计划、`created` | 快照 |
   | `settings` | 快照，但只属于这台手机的键（`LOCAL_ONLY`）保留当前的 |
   | `sync` | **当前的**（epoch 和同步基线都是当前的，绝不用快照里的旧 epoch），再加上 `hold` |
   | 冲突箱 | 当前的，并补上快照里有、当前没有的项；**当前未同步的修改**作为新项放进冲突箱（批次 `<uid>:p<时间>`，来源 `local`），不会被快照内容盖掉 |
   | `safety` | 当前的，加上保护点批次 |

3. 保护点：把当前完整账本写成快照（`kind: protect`），必须拿到严格回执。
4. 原子提交 `R`。失败时内存和存储都保持原样；保护点文件属于未提交批次，按规则保留。
5. 整个过程**不发任何网络请求**：不调用任何恢复 RPC，不写任何数据表。

### 暂停同步期间

- `C.sync` 不发任何网络请求（手动同步也一样），只提示原因。
- 不能开始云端恢复，也不能再做一次本机恢复。
- 状态写在 `S.sync.hold` 里，随账本一起持久化，重启后仍然暂停。

### 恢复云同步

强制走一次对齐（即使 epoch 没变），批次 `<uid>:<epoch>:r<时间>`，来源 `snapshot`。本机恢复出来的内容和云端不同的地方，作为冲突项让用户逐条决定，**不会自动上传**。然后本机等于云端，清除暂停状态。

### 撤销本机恢复

- 只有恢复后数据没改过才允许：用 `hold.dataHash` 判断，这是数据部分的指纹。
- 读出保护点并校验，然后原子提交它，清除暂停状态。
- 如果改过数据，就只能「恢复云同步」。这时所有改动都会进冲突箱，不会丢。

所有步骤都不经过 `addRecord` / `deleteRecord` / `rewardRecord`。

## 9. 竞态检查

| 情况 | 处理 |
|---|---|
| 两次同步同时进行 | `C.busy` 互斥（不变） |
| 等待回执期间用户改了账本 | `same()` 检查，见第 4 节 |
| 页面进程被系统回收后重载 | 等待表随页面消失；新页面里编号不认识，旧回执丢弃；状态以正式文件为准 |
| 迟到的回执 | 等待表里已经没有这个编号，直接丢弃，不触发任何覆盖 |
| 原生的普通保存和提交交错 | 同一个串行队列，按发送顺序执行（见 3.5 节） |
| 本机恢复和云端恢复同时进行 | 互相拒绝（第 8 节前置条件） |
| 清理和对齐、恢复同时进行 | 清理只删「已完成超过 30 天、没有被引用」的批次。正在使用的批次 `doneAt` 为空，或者被引用 |
| 退出登录 | 账本连同 `S.safety` 一起清空；磁盘快照保留（归属无法判断）；没生效的恢复任务按 2B-3 的方式取消 |

## 10. 恢复任务的持久化（考虑结果）

`restore.js` 的任务记录（`xm_restore_job_v1`）和待上传数据（`xm_restore_payload_v1`）仍然存在 localStorage，本轮不搬到原生文件。理由：

- 任务记录很小；
- 已应用之后即使记录丢了，下次同步按 epoch 也会自动对齐（来源会显示为 `rebase`），不会丢数据；
- 应用之前记录丢了，云端任务停在「已封存」，不会生效，也不会丢数据，只是需要用户重新导入；
- 待上传数据存不下时只放在内存里（2B-3 已经这样处理）。

**剩余风险：** 原生 App 里账本特别大时，localStorage 可能被一份过期的账本副本占满（`App.flush` 写 localStorage 失败时不会删除旧副本），导致「开始恢复」时任务记录存不进去。这种情况会**明确提示并停止**，不会发出任何恢复请求。列入阶段报告的未解决风险。
