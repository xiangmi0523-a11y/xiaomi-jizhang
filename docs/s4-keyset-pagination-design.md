# S4 残余风险：云端拉取分页的设计说明（只是设计，不含代码）

> 本文只提交设计，**没有修改任何代码、测试或数据库**。
> 对应代码：`www/js/cloud.js` 的 `pullSince`（第 243–254 行）和 `syncTable`（第 262–318 行），核对时的提交是 `313bf7b`。

## 1. 现在的做法

```js
// pullSince：每页 1000 行，按「更新时间、主键」排序，用 offset 翻页
select=*&order=updated_at.asc,<主键>.asc&limit=1000&offset=N&updated_at=gt.<since>
```

- `since` 是上一次拉到的最大 `updated_at`，过滤条件是严格大于（`gt`）。
- `syncTable` 拉完以后，把 `since` 推进到这次看到的最大 `updated_at`。只有拉下来的行会推进它，自己上传的行不会。
- 服务器端：触发器 `xm_touch_updated_at()` 在每次插入或修改时写 `updated_at := now()`。`now()` 是**事务开始的时间**，不是提交的时间。
- 索引：`(user_id, updated_at)`；主键 `(user_id, id)`，猫咪表是 `(user_id, cat_id)`。主键列都是 `text`。
- 每一页是一次独立的 HTTP 请求，也就是独立的数据库事务。**各页之间看到的数据快照不一样。**

`313bf7b` 加上主键排序以后，「同一时间的大批行在两页之间重复或遗漏」的问题已经解决（CI 测试 C6 覆盖）。剩下两个问题如下。

## 2. 残余风险

### R-a：翻页过程中有行被修改，后面的行整体前移（offset 的问题）

**过程：**

1. 设备 B 拉第 1 页（第 1–1000 行）。
2. 设备 A 修改了第 1–1000 行中的某一行 X。X 的 `updated_at` 变成最新，排到了最后。
3. 原来的第 1001 行前移成第 1000 行。
4. 设备 B 用 `offset=1000` 拉第 2 页，从原来的第 1002 行开始。**原来的第 1001 行（记为 Y）被跳过。**
5. B 这次拉到的最大时间肯定大于 Y 的时间，`since` 越过了 Y。之后的普通同步都是 `gt since`，**Y 不会再被拉到。**

**触发条件（全部满足）：**

- 一次拉取超过 1000 行，也就是要翻页。一般出现在新设备第一次同步、长时间没同步，或者另一台设备刚导入了大量数据。
- 翻页的几秒内，同一个账号在另一台设备上修改了已经拉过的行。
- 删除也算修改：删除是把 `deleted` 标成 true，同样会更新 `updated_at`。

### R-b：事务晚提交（和分页方式无关，keyset 也解决不了）

**过程：**

1. 设备 A 的一次写入事务在 t0 开始，它写的行的 `updated_at` 是 t0。
2. 这个事务在 t0+δ 才提交。
3. 在这之间，设备 B 拉取，看到了别的、时间是 t1 > t0、已经提交的行，于是把 `since` 推进到 t1。
4. A 的行提交以后，时间 t0 < `since`，**B 以后都不会拉到它。**

**触发条件：** 同一个账号同时有两个以上的写入方。例如三台设备，或者同一张表上同时有两个请求。每台设备的同步是串行的：先拉、再推，各表依次处理。所以只有一两台设备的个人使用，触发概率很低。

### 两种风险的后果

- 漏掉的行在**这台设备上缺失**：列表、统计少一条，或者一条已经删除的行还显示在本机。
- **云端不受影响：** 漏掉的行不在本机的指纹表 `tm.h` 里，所以不会被当成「本机删掉的行」去标记云端删除。
- **自动补齐只有两种情况：**
  - 这一行以后又被修改，会重新拉到；
  - 发生恢复（epoch 变化）以后整表重拉。
- 目前**没有别的自动补齐机制**。

### 顺带发现：100 页上限会静默截断（R-c）

`pullSince` 的循环是 `off < 100000`。一次要拉超过 10 万行时，会在第 100 页**静默停止**，并且照样推进 `since`，多出来的行全部漏掉，没有任何提示。现在的账本远小于这个规模，但这属于同一段代码，建议一起处理：超过上限时报错、不推进 `since`，而不是静默截断。

## 3. 方案

### 方案 K：改成按「更新时间 + 主键」续页（keyset 分页），解决 R-a

**做法：**

- **第 1 页：** 和现在一样，`updated_at=gt.<since>`，`order=updated_at.asc,<key>.asc`，`limit=1000`，不带 offset。
- **之后每页：** 用上一页最后一行的 `(ts, k)` 作为游标，只拉排在它后面的行：
  ```
  or=(updated_at.gt."<ts>",and(updated_at.eq."<ts>",<key>.gt."<k>"))
  ```
  这和数据库的行比较 `(updated_at, key) > (ts, k)` 是一个意思。PostgREST 的过滤语法不支持直接写行比较，所以拆成 `or` / `and`。
- **结束条件：** 一页不满 1000 行就结束。另设安全上限（比如 500 页），超过时**报错**，并且**不推进 `since`**（同时解决 R-c）。

**为什么能解决 R-a：** 游标是「位置」而不是「第几行」。前面的行被修改、移到最后，不会影响后面的行的位置。被修改的行 X 本身：

- 如果在后面几页之前提交，这次就会在末尾被拉到；
- 否则下次同步按 `gt since` 拉到。

**实现时必须注意的细节（都要有测试）：**

1. **时间戳原样使用。** 游标里的 `ts` 必须是服务器返回的原始字符串，精确到微秒，例如 `2026-10-28T01:02:03.123456+00:00`。**不能经过 JS 的 `Date` 转换。**
   - `Date` 只有毫秒精度，会截掉后三位。
   - 截掉以后，`eq` 匹配不到这一行，`gt` 又会把同一毫秒内的行再拉一遍。最坏的情况是同一批行反复拉取、停不下来。
   - `cloud.js` 第 255 行已经说明 Safari 解析 6 位小数秒不可靠，所以现在比较时间也是直接比较字符串。
2. **值要加引号并转义。** 时间戳里有 `.`、`:`、`+`，主键可能来自导入的备份文件，什么字符都可能有。PostgREST 的 `or` 语法里，`,`、`.`、`:`、`(`、`)` 都有特殊含义。
   - 所以值一律用双引号包起来，值里的 `"` 和 `\` 要转义；
   - 整个参数再做 URL 编码（`+` 必须编码成 `%2B`，否则会变成空格）。
3. **主键的大小比较交给数据库。** 排序和 `gt` 都按数据库的排序规则进行，两者一致。前端**不要**自己用 JS 比较主键大小，来判断「是否已经越过游标」。
4. **加上重复保护。** 同一次拉取里，同一个主键出现第二次时，以后出现的为准（`313bf7b` 在恢复后的整表拉取里已经这样处理）。如果游标没有前进（下一页第一行等于上一页最后一行），立即报错，防止死循环。

**数据库：** 不需要迁移。`or` 和 `and` 嵌套是 PostgREST 的标准功能。现有索引 `(user_id, updated_at)` 能先按时间范围定位，再在很少的同时间行里比较主键。

- 实施前，在测试库用 5 万行做 `EXPLAIN` 确认。
- 只有确认性能不够时，才考虑加 `(user_id, updated_at, <key>)` 索引。那属于数据库迁移，需要单独批准。

**兼容性：** 只改前端的拉取方式，服务器、旧版客户端都不受影响。`tm.since` 的格式不变，新旧版本可以混用，也可以降级。

### 方案 L：回看窗口，解决 R-b（可选，和方案 K 相互独立）

**思路：** 晚提交的行，时间不会早于「它提交时刻减去最长事务时长 Δ」。所以只要在 `since` 往前 Δ 的范围内**再确认一次**，就能拉到这些行。重复拉到的行会按指纹（`tm.h`）判断为没有变化，直接跳过，不会改动本机数据。

**Δ 的取值：** 普通写入是单条 upsert，或者一批不超过 500 行的 upsert。Supabase 给 `authenticated` 角色的语句超时默认是 8 秒（这是默认值，生产库的实际设置没有核实）。建议 Δ = 60 秒，留足余量。

恢复的 apply 是长事务，但恢复会改变 epoch，所有设备都会整表重拉，不依赖 `since`，所以不在 Δ 的考虑范围内。

**不能简单地每次都从 `since − Δ` 开始拉：**

- 恢复或导入以后，几万行的时间完全相同。
- 只要之后没有新的修改，`since` 就一直停在这个时间。
- 每次同步都会把这几万行重新下载一遍。

**建议的做法：只补查一次。**

- 每次拉取完成后，记下一个「待补查」标记 `tm.recheck = { from: <这次拉取前的 since>, at: <本机时间> }`。
- 下一次拉取的下限改用 `min(since, recheck.from) − Δ`。
- 拉取成功，并且距离 `recheck.at` 已经超过 Δ，就清掉这个标记。
- 这样每个时间段最多被补查一两次，不会一直重复下载。
- 这里只用到本机时间的**差值**，不需要和服务器时间对齐。
- 本机时间被调整的最坏结果是多补查一次，或者补查得太早。补查太早时，那一行要等它下次被修改才会被拉到，等于退回到现在的状态，**不会比现在更差**。

**彻底的服务器端方案（不推荐本阶段做）：** 用提交顺序而不是开始时间来排序，例如基于事务快照 `pg_current_snapshot()` 的游标，或者开启 `track_commit_timestamp`。都需要新的 RPC 或者改数据库配置，要在生产库执行迁移，超出本阶段的范围。

### 不采用的做法

| 做法 | 不采用的原因 |
|---|---|
| 只把每页加大到 1 万行 | 只是降低概率，也有超时和内存的风险 |
| 拉完以后再按 offset 重拉一遍做核对 | 流量翻倍，而且核对时同样会有并发修改 |
| 新增服务器 RPC，在一个事务里分页返回所有行 | 需要生产迁移；大账本单个事务的时长和内存都难以控制 |
| 触发器改用 `clock_timestamp()` | 时间仍然早于提交时间，不能解决 R-b，还需要生产迁移 |

## 4. 并发修改测试计划（实施时使用）

- 网关已经提供请求前后的钩子（`gw.before` / `gw.after`），可以在两页之间插入数据库操作。

## 5. 评估和建议

| | 方案 K（keyset） | 方案 L（回看窗口） |
|---|---|---|
| 解决的问题 | R-a；连同上限问题 R-c | R-b |
| 改动范围 | 只改 `pullSince` 一个函数（约 30 行）和测试 | `syncTable` 多一个字段，加补查逻辑（约 20 行） |
| 需要数据库迁移 | 不需要 | 不需要 |
| 发生概率（个人使用，1–2 台设备） | 低。需要大批拉取，同时另一台设备在修改 | 很低。需要至少两个写入方同时写 |
| 后果 | 单台设备静默少一行，云端不受影响 | 同左 |

**建议：**

1. 两项都**不在本阶段实施**，符合「不扩大本阶段范围」的要求。
2. 方案 K（连同 R-c 的上限报错）作为一个独立的小改动，排在真机验收之后、正式发布之前，或者作为发布后的第一个修正版。由架构师决定。实施时按第 4 节先写 T1、T2，确认它们在现有代码上失败，再改代码。
3. 方案 L 可以和 K 一起做，也可以延后。延后的话，在第三阶段的风险说明里写明：「多台设备同时写入时，极少数情况下某台设备可能少同步一条，恢复同步后整表重拉可以补齐」。
4. 在修复之前，这个风险已经记录在风险清单（`docs/risk-register.md`）里。
