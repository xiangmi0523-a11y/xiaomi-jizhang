# H3 备份恢复 · 状态机与服务端协议（修订版，Phase 2A）

状态：设计已原则通过；本文件随 `supabase/restore_epoch.sql` 一起提交审核。**未在生产执行，前端未实现。**

## 0. 相对上一版设计的关键修改

| 上一版 | 修订版 | 原因 |
| --- | --- | --- |
| 客户端分批 upsert / 软删除正式表，期间服务器长时间持锁 | 客户端只把备份上传到**暂存区**；由一个 RPC 在**单个数据库事务**里完成「存档 → 覆盖 → 软删除 → 核对 → 版本号 +1」 | 正式表只有「完全未改」和「完全改好」两种状态，不存在半成品账本；没有长时间的锁，也就不需要心跳、超时、接管锁 |
| `begin` 时 epoch +1 | **只在应用成功的那一刻** epoch +1 | 取消、失败、断网都不改变 epoch，旧版客户端不受影响；只有恢复真正生效后旧版才被挡住 |
| 每行一个 `client_epoch` 列作为通行证 | 写入时带请求头 `x-xm-epoch`，触发器从 PostgREST 的 `request.headers` 读取 | upsert 不带某列时 PostgreSQL 会沿用旧值，列方案会让旧版「借用」上次的版本号；请求头每次请求都要重新提供 |
| `finish` 只核对条数与 epoch | 应用事务内用 SQL **逐行比对**正式表与暂存区（键集合 + 规范化后的整行内容），整块设置按模块比对 | 能识别「条数相同但 ID 或内容不同」 |
| 接管 = 放弃别人的锁 | 接管 = 同一账号的任何设备都可以对**已封存**的任务执行 `apply`（幂等）；未封存的任务只能取消，且它从未碰过正式表 | 安全接管并继续同一任务；不存在「只清锁就恢复普通同步」的路径 |

## 2. 服务端对象（`supabase/restore_epoch.sql`）

- `xm_meta(user_id, epoch)`：每个账号一行，epoch 从 0 开始，只增不减。客户端只读自己的一行。
- 五张数据表各加 `epoch int`：由触发器写入，记录这一行是在哪个版本下写的，客户端提供的值一律被覆盖。
- `xm_restore_job`：恢复任务（`staging → sealed → applied`，或 `staging/sealed → cancelled`）。客户端只读自己的任务。
- `xm_restore_stage`：暂存区，每行带客户端给的内容指纹 `h`。客户端无任何直接权限。
- `xm_restore_archive`：应用前的全部旧行和旧整块设置，**永不自动清理**，给将来的撤销功能用。客户端无任何直接权限。
- 写入保护触发器 `private.xm_guard_write`（五张表，BEFORE INSERT/UPDATE/DELETE）：
  - 只对 `authenticated` / `anon` 角色检查；数据库内部（恢复事务、后台管理）走受信路径。
  - 以共享锁读取 `xm_meta`，与应用事务的排他锁串行。
  - epoch = 0（从未恢复过）：全部放行，旧版客户端照常使用。
  - epoch > 0：请求头 `x-xm-epoch` 必须等于当前 epoch，否则报 `PT409`（HTTP 409），提示「请更新后再同步」；硬删除一律拒绝。
- RPC（全部 `security definer`、`search_path = ''`、只授权 `authenticated`、每次校验 `auth.uid()` 与任务所属）：

| RPC | 作用 | 幂等 / 并发 |
| --- | --- | --- |
| `xm_restore_create(job, scope)` | 建任务，记下当时的 epoch | 同 id 同范围重复调用返回原任务；他人的 id 一律当作不存在 |
| `xm_restore_stage(job, table, rows)` | 上传一批（≤ 500 行）到暂存区，逐行校验列名、类型、非空 | 同键覆盖；与封存用任务行锁串行，封存后拒绝 |
| `xm_restore_seal(job, manifest, state_patch)` | 封存：服务器重算每张表的条数和「键+指纹」摘要，必须与清单一致；记下整块设置补丁 | 同清单重复调用返回原结果 |
| `xm_restore_apply(job, expected_epoch)` | 单事务应用（见第 3 节） | 已应用的任务直接返回原结果；两个任务竞争时只有一个成功，另一个得到 `epoch_changed` |
| `xm_restore_cancel(job)` | 取消未应用的任务并清空暂存 | 已取消的重复调用无副作用；已应用的不能取消 |

## 3. `xm_restore_apply` 事务内的步骤

1. 确保 `xm_meta` 行存在，`SELECT … FOR UPDATE` 锁住。之后任何普通写入都要等待，等到时会读到新的 epoch 并被拒绝。在此之前已经通过检查的写入，会先提交，算作「恢复前的云端」。
2. 锁住任务行：已应用 → 直接返回原结果；不是 `sealed` → 报错；epoch ≠ `expected_epoch` → `epoch_changed`。
3. epoch +1。
4. 对范围内每张表：把该用户的全部现有行存档 → 用暂存区 upsert（`deleted = false`）→ 暂存区没有的未删除行改为 `deleted = true` → **逐行核对**：未删除行与暂存区在「键 + 规范化整行内容」上双向差集为空，并且每个未删除行的 epoch 都是新值。
5. 整块设置：存档旧 data → 顶层合并补丁 → 核对补丁里的模块等于补丁、补丁外的模块等于旧值且一个不少。
6. 任一核对失败 → 抛错 → **整个事务回滚**：正式表、epoch、存档、任务状态都不变。
7. 任务置为 `applied`，返回新 epoch 和各表条数。

注意：`updated_at` 由已有触发器取事务开始时间，可能早于并发提交的写入；因此客户端**不能**用时间戳判断恢复结果，一律以 epoch 变化触发全量对齐（第 4 节）。

## 4. 客户端状态机（前端下一阶段实现，本阶段只用测试驱动验证协议）

发起设备 A：

| 状态 | 进入条件 | 成功条件 → 下一状态 | 失败 / 中断 |
| --- | --- | --- | --- |
| 校验 | 用户选了备份文件 | 必需模块齐全、`normalize` 不丢任何记录、id 不重复、新格式清单相符 → 确认页 | 拒绝，什么都不改 |
| 确认 | — | 用户确认（确认页写明：恢复成功后，没更新的旧版 App 将无法同步） | 取消 |
| 建任务 | — | `create` 返回任务（记下 `expected_epoch`）→ 暂存中 | 网络错误：重试同一 job id |
| 暂存中 | 本机持久化任务（job id、备份内容、已传批次） | 全部批次传完 → 封存 | 任一批失败：从失败批次继续，同键覆盖不影响结果 |
| 封存 | — | `seal` 成功 → 已封存 | 清单不符：重传全部批次后再封存 |
| 已封存 | — | `apply` 成功 → 本机全量对齐 → 完成 | 网络错误或响应丢失：重试 `apply`（幂等）；`epoch_changed`：告诉用户「另一台设备刚恢复过」，让用户选择取消，或者在新 epoch 上重新建任务 |
| 完成 | — | 删除本机任务记录，按新 epoch 恢复普通同步 | — |

- 任务存在期间，A 不走普通同步，避免把恢复前的云端数据拉回本机。
- App 被杀后重启，从持久化的状态继续。
- 另一台设备看到自己账号下有已封存的任务，可以继续执行（接管）或取消；看到暂存中的任务只能取消（暂存区从未碰过正式表）。

其他设备 B：每次同步先读 `xm_meta.epoch`。
- 与本机记录的相同：普通同步，写入带 `x-xm-epoch`。
- 比本机新：存快照，找出恢复前未同步的修改放进冲突箱，全量拉取替换本机，记下新 epoch，再恢复普通同步。
- 写入收到 409：重读 epoch，按上一条处理。

## 5. 版本号与旧版客户端

- epoch 只在 `apply` 成功时增加。取消、封存失败、应用失败、断网都不改变 epoch，旧版客户端照常同步。
- 恢复成功后（epoch ≥ 1），旧版客户端的所有写入被拒，直到更新 App。确认页必须提前说明。
- **没有**「失败后让旧版继续写入」这种回滚：写入保护一旦对某个账号生效就不撤销。

## 6. 回滚脚本（`supabase/restore_epoch_rollback.sql`）

- 先锁住 `xm_meta`，阻止回滚期间有人完成恢复。
- **从未有账本应用过恢复**（所有 epoch = 0 且没有 `applied` 任务）：完整删除本迁移新增的全部对象，回到迁移前的结构。
- **已有账本应用过恢复**：拒绝完整回滚；只撤销 5 个恢复 RPC 的执行权限（停止新的恢复），**保留**触发器、`xm_meta`、epoch 列和存档，旧版客户端仍然被挡住。
