# 本机安全快照方案评估（Phase 2B 审核意见 · 只评估，未实施）

> 分支 `feat/h3-frontend`。本文只做调查、方案比较和测试计划：
> - 没有修改业务代码和数据库迁移；
> - 没有加载或批准 `supabase/proposals/2b3-restore-apply-timeout.sql`；
> - 没有合并 main，没有生产操作，没有发布或部署。
>
> 目标只有一个：云端恢复已经成功，但本机安全快照写不进 localStorage，本机就无法完成对齐。要解决这个问题。

## 0. 结论先行

- **推荐：方案 A，iOS 原生文件快照加明确的持久化回执。** 理由：
  - 原生 App 是主要使用场景；
  - 文件写到 App 的 Documents 目录，容量受手机剩余空间限制，而不是 5MB；
  - 可以做到写完强制落盘（fsync）、读回校验 sha256 之后才回执，是三个方案里唯一能对「已持久化且可恢复」给出可验证回答的；
  - 前端和原生代码打包在同一个 IPA 里，不存在新旧版本混用。
- 网页版和 PWA 这一阶段**保持现状**：仍用 localStorage，写不进去就安全停下并说明原因。方案 B（IndexedDB）可以以后单独评估，用于网页版，但需要先在真机和各浏览器上验证。
- **不推荐方案 C 作为快照机制。** 它要求「差异计算」和「覆盖逻辑」逐项一致，错一处就会静默丢数据，而快照本来就是用来兜住这类错误的。最坏情况（恢复到很旧或很小的备份）下差异接近整份账本，并不能解决容量问题。
- **不管选哪个方案，都必须一起修的两件事：**
  1. 冲突箱的持久化（`protect`）目前同样要求整份账本写进 localStorage。只修快照，卡住的门槛只会从约 1.8 万笔提高到约 3.6 万笔；
  2. 快照目前只保留一份、原生快照文件不清理，需要按批次保存，并制定清理规则。

## 1. 现状：读代码和实测的发现

### 1.1 现在的对齐流程（`www/js/cloud.js` `C.rebase`，第 408 行起）

1. `App.conflicts.snapshot(batch, label)`（第 411 行）：把整份账本写进 `localStorage['xm_snap_rebase']`。**失败就抛错，后面都不执行。** 另外再发一个原生 `snapshot` 消息写文件。
2. 全量拉取云端各表和 `xm_state`，这一步不改本机。拉完再读一次 epoch，如果变了就停下。
3. 下面在同一段同步代码里完成，中间没有 `await`：
   - `pendingChanges()`（第 419 行）；
   - `protect()`（第 420 行）：写冲突箱，并 `persistNow()` 把整份账本写进 localStorage，**失败就抛错**；
   - 覆盖各表（第 430 行）、`stateIn`（第 434 行）；
   - `epoch = target`（第 437 行）；
   - `prune`（第 438 行）。
4. `C.sync` 结束时 `App.flush()`：写 localStorage（**吞掉错误**）和原生 `save`（**没有回执**）。

### 1.2 实测（本环境 Chromium，与业务代码无关的测量脚本）

| 项目 | 结果 |
|---|---|
| localStorage 每个来源的上限 | **5,242,880 个字符**左右。中文和英文一样按字符计 |
| 每笔账单在账本 JSON 里的大小 | 约 144 个字符（含中文备注的典型记录） |
| 账本 + 快照两份能放下的上限 | 约 **1.8 万笔**。上一阶段实测：1.6 万笔的测试账单，第二份就写不进去了 |
| 只放一份账本（`protect` 的门槛） | 约 **3.6 万笔** |
| IndexedDB（Chromium） | 写入并读回 500 万个汉字正常；`navigator.storage.estimate()` 配额约 468 MB |
| WebKit | **本环境没有 WebKit**（不允许另装浏览器）。iOS 上的配额和计数方式**必须真机实测**，不能按 Chromium 推断 |

### 1.3 关键代码事实

- **F1 原生层没有任何回执。** `ViewController.swift`：
  - `saveSnapshot`（第 347 行）和 `saveData`（第 476 行）都用 `try? Data(...).write(..., options: .atomic)`，**失败被吞掉**，也不回调网页；
  - `.atomic` 是「写临时文件再改名」，**不做 fsync**；
  - 网页端 `App.native()`（`core.js`）返回 `true` 只表示 `postMessage` 交出去了，不代表文件写成功。
- **F2 现在不会把原生写入误当成成功。** `conflicts.js` 的 `snapshot`（第 33 行）只以 localStorage 写入成功为准，原生文件只是附带。但 **localStorage 的 `setItem` 返回成功，也只代表交给了浏览器的存储层**，WebKit 和 Chromium 都是异步写盘。App 被杀或断电时，最近的写入能不能留下来，需要真机验证（见测试 T-D3）。
- **F3 冲突箱持久化有同样的容量门槛。** `persistNow`（`conflicts.js` 第 25 行）先写 localStorage，失败就抛错，原生 `save` 同样没有回执。所以单份账本超过约 3.6 万笔时，冲突箱也写不进去，对齐同样会停。
- **F4 快照会被覆盖，原生快照会无限增长。**
  - localStorage 只有一个快照键 `xm_snap_rebase`：恢复对齐和普通对齐连着发生时，后一次会覆盖前一次。
  - 原生端的清理规则（第 356 行）只清「自动备份」和「操作前备份」两类，「对齐前备份」「恢复前备份」**从不清理**，每份都是整份账本。
- **F5 没有「从快照恢复本机」的入口。** 现在只能在「文件」App 里找到快照文件，再用「导入备份」导入。登录状态下这会走云端恢复，并不是「只恢复本机」。
- **F6 启动时优先读原生文件**（`App.load`，`core.js` 第 187 行）。原生 `save` 如果静默失败，重启后会读到较旧的文件。对「对齐」来说这是安全的：旧文件里的 epoch 也是旧的，会重新对齐一次，冲突项按批次编号合并、不会重复。但 localStorage 里更新的内容会被忽略。这是已有的问题，本文不处理，只列出来。
- **F7 对齐本身可以重复执行。**
  - 批次编号是 `用户:目标 epoch`，冲突项的编号是 `批次|表|键`；`protect` 遇到相同编号只更新，不重复生成；已经处理过的项不再改动。
  - 「加回去」直接改数组，不经过记账、删除和奖励的入口。
  - 所以重启后重新对齐不会重复生成记录，也不会重复发奖励。
  - 但如果期间目标 epoch 又变了（新批次），同一笔本机修改会在两个批次各出现一次。处理时按编号覆盖，不会生成重复账单，但界面上会显示两条。
- **F8 测试用的 IPA 没法「只构建不发布」。** `.github/workflows/build-ipa.yml` 在手动触发时也会执行「发布到 Releases」。方案 A 的真机测试需要一个**只构建、不发布**的工作流，这需要审核。
- **F9 云端有存档。** 恢复引起的对齐，被替换掉的云端旧行已经保存在 `xm_restore_archive` 里（客户端无权读取，永不自动清理）。本机快照的作用是：保护「本机独有」的内容，以及在差异计算本身出错时兜底。

## 2. 任何方案都必须满足的不变式

| 编号 | 不变式 |
|---|---|
| I1 | 快照被**确认「已持久化且可恢复」**之前，不覆盖任何本机数据，也不更新 epoch |
| I2 | 冲突箱被确认持久化之前，不覆盖 |
| I3 | 存储里的账本只能**原子地**从「覆盖前」跳到「覆盖后（含冲突箱、新 epoch）」，不能出现只写了一半的状态。重启后读到的要么是覆盖前，要么是覆盖后 |
| I4 | 快照按批次（`用户:目标 epoch`）保存，不覆盖其他批次。保留到该批次的冲突全部处理完，再加 30 天 |
| I5 | 「成功」只能来自明确的确认（字节数 + sha256 一致）。没有确认、超时、内容不一致，一律算失败 |
| I6 | 失败时：不覆盖、不改 epoch、提示具体原因、可以重试。普通写入仍被 epoch 机制挡住，不会以旧版本写云端 |
| I7 | 对齐、冲突处理都不经过 `addRecord` / `deleteRecord` / `rewardRecord`，不改金币、签到、盲盒进度、猫咪 |
| I8 | 快照能被用户找回：「文件」App 里可见，并且有一个「从快照恢复本机」的入口（只恢复本机、不碰云端） |

## 3. 方案 A：iOS 原生文件快照 + 持久化成功回执

### A-1 会修改的文件、模块、接口

| 位置 | 改动 |
|---|---|
| `ios/Sources/SnapshotStore.swift`（新） | 写快照：先写临时文件，`FileHandle.synchronize()` 加 `fcntl(F_FULLFSYNC)` 强制落盘，再改名为正式文件并同步目录；然后**重新读出文件**，用 CryptoKit 算 SHA-256，与网页给的值比对。另外负责：启动时清理残留的临时文件；按批次列出、读取、清理快照 |
| `ios/Sources/ViewController.swift` | 新消息：<br>• `snapshotWrite {id, batch, filename, content, bytes, sha256}`<br>• `ledgerSave {id, content, bytes, sha256}`：带回执的账本保存，给 `protect` 和覆盖后保存用<br>• `snapshotList` / `snapshotRead`：给恢复入口用<br>回执：`App.native.done(id, ok, info, err)`，网页端回调<br>启动脚本加 `window.__NATIVE_CAPS__ = { durableWrite: 1 }`<br>修改清理规则：对齐 / 恢复前的快照按批次清理，不按文件名前缀 |
| `www/js/conflicts.js` | `snapshot` 改成异步：有原生能力时等原生回执，没有时走 localStorage（与现在相同）。`persistNow` 有原生能力时以带回执的 `ledgerSave` 为准，localStorage 只是附带。快照按批次命名、按 I4 保留。新增「从快照恢复本机」入口 |
| `www/js/cloud.js` | `C.rebase`：`await App.conflicts.snapshot(...)`；`protect` 加覆盖改为「先把覆盖后的账本整份在内存里算好 → 一次带回执的保存 → 回执成功才把内存切换过去」，满足 I3 |
| 原生请求的通用封装 | 放在 `conflicts.js`，不改 `core.js`，按 `App.http` 的方式：编号 + 等待表 + 超时 |
| 只改文案 | `www/js/restore.js`，快照失败时的提示 |
| 其他 | `www/sw.js`（重新生成）；测试夹具 `NATIVE_STUB` 增加回执模拟；`project.yml` 增加 XCTest 目标；新增一个只构建不发布的工作流（需审核） |

### A-2 如何保证快照写成功才覆盖

前端在把 `content` 交给原生层之前，先算好 `bytes`（UTF-8 字节数）和 `sha256`。用 `restore.js` 里已有的纯 JS SHA-256，已与 Node `crypto` 对照过 359 组。

原生层只有在下面四步**全部完成**后才回执 `ok: true`，并在回执里带上它**从磁盘读回的文件**算出来的字节数和 sha256：

1. 写临时文件；
2. fsync；
3. 改名为正式文件并同步目录；
4. 读回文件，与网页给的字节数、sha256 都一致。

前端只在 `ok === true`、回执编号是自己发出去的、读回的字节数和 sha256 与自己算的一致时，才算成功。**任何其他情况都算失败**，包括：超时（建议 30 秒，按大小放宽）、页面重新加载导致等待表丢失、编号不认识。

### A-3 各种中断如何恢复

| 情况 | 结果 |
|---|---|
| 写快照时被杀或断电 | 正式文件还没出现（最多残留临时文件，下次启动清理）。网页没收到回执 → 没覆盖 → 重启后 epoch 仍是旧的 → 再走一次对齐，重新写快照 |
| 原生已写完、回执还没到网页就被杀 | 同上，重新对齐。同一批次会多一份内容相同的文件，清理时按 sha256 去重 |
| 存储空间不足 | 写入抛错 → 回执 `ok: false, err: 'ENOSPC'` → 提示「手机存储空间不足，需要约 X MB」，不覆盖，可以重试 |
| 重复重试 | 每次都是「临时文件 → 改名」，结果相同；冲突项按编号合并（F7） |
| 网页进程被系统回收（第 161 行会重新加载页面） | 旧页面的等待表随之消失；原生层之后发来的回执在新页面里编号不认识，直接忽略 → 当作没成功，重新对齐 |
| 恢复后重新启动 | 恢复任务在 `xm_restore_job_v1` 里仍是「已应用」→ 下次同步继续对齐（与 2B-3 相同） |

### A-4 云端已恢复、本机快照或对齐失败时如何安全重试

- 本机账本保持不动，epoch 保持旧值。每次同步都会经过 `checkEpoch` 进入对齐，自动重试；进度面板上也有「现在重试」。
- 在这期间普通写入会被服务器以 409 拒绝，`C.writeEpoch` 也不会用错的版本号写。用户在本机新记的账，留在本机，等对齐时进冲突箱。
- 如果是空间不足：提示需要多少空间；腾出空间后重试即可。

### A-5 如何保护未同步的账单、编辑、删除、预算、存钱计划、金币和冲突箱

- **快照：** 整份 `App.S`，包括 `records`、`accounts`、`cats`、`budget`、`recurring`、`game`（含金币、签到、盲盒进度、猫咪）、`smart`、`saving`、`settings`、`created`、`sync`、`conflicts`。写成文件并确认之后才开始覆盖。
- **冲突箱：** 未同步的新增、编辑、删除和整块设置模块，由 `pendingChanges` 收集，放进覆盖后的账本里，**一次带回执保存**（I3）。回执成功之前内存不切换，存储里仍是覆盖前的账本。
- **原则：** 冲突箱是「逐条处理」用的，快照是「整体兜底」用的。两者都要确认落盘。

### A-6 如何防止重复奖励、重复记录和快照覆盖

- **奖励：** 不变（I7）。
- **重复记录：** 冲突编号按批次合并；「加回去」按编号覆盖。另外增加跨批次去重：新批次里如果有和旧批次待处理项「同一张表、同一个键、本机内容相同」的项，就不再新建。
- **快照覆盖：** 每个批次一个目录，不同批次不互相覆盖。清理规则只删「冲突全部处理完、并且超过 30 天」的批次。

### A-7 平台差异

| 平台 | 行为 |
|---|---|
| iOS 原生 App | 走原生快照：容量受手机剩余空间限制；快照在「文件 → 我的 iPhone → 晓米记账」里可见；会随 iPhone 备份一起备份 |
| PWA（添加到主屏幕）和普通浏览器 | 没有原生层，`__NATIVE_CAPS__` 不存在 → 仍走 localStorage，行为与现在相同：写不进去就安全停下，并提示「账本太大，网页版无法完成对齐，请用 App 或清理浏览器数据」。以后可以叠加方案 B |
| 旧 IPA 搭配新网页 | 不会出现：原生 App 的网页文件打包在 IPA 里。网页版（Vercel）本来就没有原生层 |

见第 7 节：T-A1 到 T-A6，加通用的 T-C1 到 T-C12。

### A-9 复杂度、风险、维护成本

- **复杂度：中。** Swift 约 150 到 200 行（含 XCTest），JS 约 150 行，新增测试约 15 项。
- **风险：**
  - 要重新打包 IPA，并用全能签重新签名安装；
  - Swift 代码在本环境里没法编译和运行，需要 macOS runner 和真机；
  - 回执协议写错会导致「永远不成功」。这是安全方向的失败（只会停下来，不会丢数据），测试也能抓到。
- **维护：** 两条路径（原生、网页），但接口很小（写入、读取、列出、回执），原生代码集中在一个文件里。

## 4. 方案 B：安全快照存进 IndexedDB

### B-1 会修改的文件、模块、接口

| 位置 | 改动 |
|---|---|
| `www/js/conflicts.js`（或新增一个小模块） | IndexedDB 数据库 `xm_safety`，表 `snapshots`，以批次为键。`snapshot` 改成异步：等事务真正完成（`complete` 事件，而不只是请求成功），并尽量要求严格落盘（`durability: 'strict'`）；再用一个新事务读回，校验 sha256 后才算成功 |
| `www/js/cloud.js` | 等快照完成，与 A 相同 |
| `www/js/restore.js` | 只改文案 |
| 其他 | `www/sw.js`；测试 |
| 原生层 | 不改 |

注意：方案 B **不解决 F3**。`protect` 仍要求整份账本写进 localStorage，单份账本约 3.6 万笔的门槛还在。要解决，就得把账本主副本也搬进 IndexedDB，那是对核心存储（`core.js` 的 `App.load` / `App.flush`）的重构，超出本次范围。

### B-2 如何保证写成功才覆盖

以「事务 `complete` 加读回 sha256 一致」为成功条件。请求成功、超出配额（`QuotaExceededError`）、事务中止、超时，都算失败。

但是：Chromium 默认的事务是「宽松落盘」（不 fsync）。`durability: 'strict'` 在 WebKit 上是否支持、是否真的强制落盘，**需要真机验证**。如果不支持，「complete 之后断电」仍可能丢失。

### B-3 各种中断如何恢复

| 情况 | 结果 |
|---|---|
| 写入中被杀或断电 | 事务没完成就整体回滚；网页没得到确认 → 没覆盖 → 重启后重新对齐 |
| `complete` 之后马上被杀 | 取决于 WebKit 存储进程是否已经写盘。iOS 上 App 被杀时它的 WebKit 子进程也会被结束，**需要真机实测**（T-B3） |
| 空间不足 | `QuotaExceededError` → 提示，不覆盖，可以重试 |
| 重复重试 | 同一批次同一个键，直接覆盖写入，结果相同 |

### B-4 云端已恢复、本机失败时如何重试

与 A 相同：本机不动，epoch 不动，每次同步自动重试，面板上可以手动重试。

### B-5 如何保护各类数据

快照内容与 A 相同（整份账本）。冲突箱仍走现在的 localStorage 路径，受 F3 的门槛限制。

### B-6 防重复

与 A 相同：批次为键、跨批次去重、奖励不变。

### B-7 平台差异

| 平台 | 情况 |
|---|---|

### B-8 测试

### B-9 复杂度、风险、维护成本

- **复杂度：低到中。** JS 约 120 行，不改原生层，不需要重新打包 IPA（网页版）。
- **风险：** 原生 App 上的兼容性和落盘保证都是未知数，而且 iOS 上的 IndexedDB 历史问题较多；冲突箱的门槛（F3）还在。
- **维护：** 一条路径，所有平台通用。但要长期关注各 iOS 版本的 IndexedDB 行为。

## 5. 方案 C：只保存即将被覆盖的部分

### C-1 必须覆盖的范围（逐项对照现在的覆盖逻辑）

对齐会改动的东西，以及部分快照必须相应保存的内容：

| 会被改动的 | 部分快照必须保存 |
|---|---|
| 四张表（账单、账户、分类、猫咪）：`t.write(list)` 整表替换 | 本机有、云端没有的项（会被删掉）；两边都有、但 `rowHash` 不同的项（会被替换）；云端有、本机没有的键清单（回滚时要删掉）。<br>还要照搬每张表 `write` 的特殊规则，例如分类：某一类在云端是空的，就保留本机的；账户、分类的顺序（`_sort`）也算内容 |
| `stateIn`（`cloud.js` 第 226 行） | `budget`、`recurring`、`smart`、`saving` 整块；`game`（不含猫咪）整块；`settings` 里不属于本机专有的键；`created` |
| `stateIn` 末尾调用的 `App.normalize(S)` | **它可能改动所有模块**：清洗账单、截断金币、补默认值。所以在「覆盖前」和「normalize 之后」之间，任何发生变化的字段都要保存 |
| `S.sync` | 整份（各表基线 `t`、`epoch`、`at`），很小 |
| `S.conflicts` | 整份。它不会被覆盖，但会和覆盖一起写入，要能回滚 |

不会被改动的：`settings` 里只属于本机的键（`LOCAL_ONLY`）、`v`。

### C-2 如何保证写成功才覆盖

部分快照仍要存进某个地方：localStorage（现状），或者 A、B 的存储。它本身不提供落盘保证，**只是让快照变小**。

### C-3 中断和恢复

与它所用的存储相同。另外需要新写「用部分快照回滚」的代码，这段代码本身也要测试。

### C-4 容量

- 一般情况（只差几十笔）：快照很小。
- **最坏情况：恢复到一份很旧、很小、甚至是空的备份**，本机几乎所有账单都会被删除，部分快照约等于整份账本。所以 C **单独并不能解决** 1.6 万笔以上的问题。

### C-5 到 C-7（保护、防重复、平台）

保护范围取决于 C-1 的对照有没有遗漏；防重复与 A 相同；没有平台差异，但容量仍受所用存储限制。

### C-8 测试

见第 7 节 T-X1 到 T-X3：随机生成本机和云端状态，做差异 → 覆盖 → 回滚，结果必须与原始状态完全一致。

### C-9 复杂度、风险、维护成本

- **复杂度：中到高。**
- **风险：最高。** 差异逻辑必须和覆盖逻辑逐项一致，`normalize` 的副作用很难穷举。差异算错的直接后果是静默丢数据，而这正是快照原本要兜住的错误。差异逻辑和 `pendingChanges` 用同类计算，两者可能**一起出错**。
- **维护：最高。** 以后每改一次 `TABLES`、`stateIn` 或 `normalize`，都要同步修改快照逻辑和测试。

## 7. 特别回答：原生层没有回执时，前端会不会误以为快照成功？

**现在的代码不会。** `conflicts.js` 只以 localStorage 写入成功为准，原生文件只是附带，不参与判断（F2）。

**但如果按方案 A 改造时处理不当，会。** 可能出错的地方有四处：

1. `App.native()` 返回 `true` 只表示消息交出去了。如果把它当成功，就会误判。
2. 现在的 Swift 代码用 `try?` 写文件，失败不报告，回执里也就不会有失败（F1）。
3. `Data.write(.atomic)` 不做 fsync，「写成功」也不等于断电后还在。
4. 网页进程被回收后页面会重新加载，旧请求的回执可能落到新页面上。

**避免办法**（全部写进实现和测试，缺一不可）：

- 成功**只能**来自原生层主动发来的回执，而且 `ok === true`、编号与发出的请求一致。`App.native()` 的返回值、`postMessage` 不报错、计时器到点，**都不算成功**。
- 回执里必须带原生层**从磁盘读回的文件**算出来的字节数和 sha256，前端与自己事先算好的值比对，不一致就算失败。这样「原生层说成功但文件不对」的情况也能抓住。
- 原生层回执成功之前必须完成：fsync 临时文件 → 改名为正式文件 → 同步目录 → 读回校验。Swift 代码里不允许出现 `try?` 吞错误：任何一步抛错都必须回执失败。
- 有超时：到点没收到回执就算失败，之后迟到的回执直接忽略。
- 用启动脚本声明能力（`window.__NATIVE_CAPS__.durableWrite`）。没有这个声明，就不走原生路径。
- 网页重新加载后等待表是空的，编号不认识的回执一律忽略。
- 测试里专门放一个「原生层回执成功、但 sha256 不对」和一个「永远不回执」的模拟（T-A1），必须都判为失败、本机不被覆盖。

## 8. 推荐方案和理由

**推荐 A**，同时一起完成这几件配套工作：

1. **冲突箱持久化**改用同一个带回执的保存（解决 F3）。
2. **快照按批次保存**，原生快照按批次清理（解决 F4）。
3. **「从快照恢复本机」入口**（I8 / F5）。
4. **网页版和 PWA**维持现在的安全停止，并改进提示文案。

**理由：**

- 原生 App 是主要使用场景。A 是唯一能对「快照已持久化且可恢复」给出可验证回答的方案。
- A 同时能解决冲突箱的容量门槛，B、C 都不能。
- A 失败的方向是安全的：没有回执就不覆盖。逻辑简单，测试容易写全。
- 前端和原生代码在同一个 IPA 里，不存在版本混用。

**不选 B 作为主方案：** `xiaomi://` 协议下 IndexedDB 能不能用、落盘强度如何、被杀之后数据还在不在、会不会被系统清掉，目前都是未知数；而且解决不了冲突箱的门槛。以后可以单独作为网页版的增强来评估。

**不选 C：** 它把「不丢数据」押在一段复杂的差异逻辑上，最坏情况也不能缩小快照，维护成本最高。

**需要架构师决定的事项：**

- **D1** 是否批准方案 A 进入设计细化和实施。
- **D2** 是否允许新增一个**只构建、不发布**的 IPA 工作流，用于真机测试（F8）。
- **D3** 网页版和 PWA 这一阶段是否接受「账本太大时安全停止，并提示用 App」。
- **D4** 快照保留规则：批次冲突全部处理完后再保留 30 天，是否合适。
- **D5** 「从快照恢复本机」入口是否纳入这一轮。
